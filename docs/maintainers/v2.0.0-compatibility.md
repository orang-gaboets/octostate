# v2.0.0 Compatibility Notes

Octostate v2 establishes required expected-organization binding for live GitOps
operations. The v1 CLI, reusable workflow, and Go APIs retain their prior
contracts; migrate callers when upgrading them to v2.

## CLI migration

Pass the organization authorized by the caller independently from
`organization.yaml` to every live plan, apply, or audit pull command:

```bash
expected_org="${OCTOSTATE_EXPECTED_ORG:?set a trusted organization target}"

octostate config plan --config-dir ./config --expected-org "$expected_org"
octostate config apply --config-dir ./config --expected-org "$expected_org" --check
octostate config apply --config-dir ./config --expected-org "$expected_org"
octostate audit pull --config-dir ./config --state-dir ./state --expected-org "$expected_org"
```

Every `config apply` mode, including `--dry-run`, requires the flag because it
loads live GitHub state. Missing, empty, invalid, and mismatched values fail
before authentication or live GitHub calls. Keep the expected value in trusted
caller configuration. Do not copy it from the desired-state document.

## Reusable workflow migration

The reusable `config-review.yml` workflow now requires `expected_org` and
always forwards it to both `config plan` and `config apply --check`. Remove the
former `bind_expected_org` input; v2 has no unbound fallback.

```yaml
jobs:
  config-review:
    uses: orang-gaboets/octostate/.github/workflows/config-review.yml@<reviewed-workflow-commit>
    with:
      config_dir: ./config
      octostate_version: <reviewed-40-character-cli-commit>
      expected_org: ${{ vars.OCTOSTATE_EXPECTED_ORG }}
    secrets:
      octostate_token: ${{ secrets.OCTOSTATE_TOKEN }}
```

The caller must set `OCTOSTATE_EXPECTED_ORG` as trusted repository or
organization configuration. An unset or empty variable fails before the live
plan step. The workflow and CLI commit pins remain independent; select and
review compatible v2 commits for both.

Audit custom workflows that install Octostate directly as well as reusable
workflow callers. Search for every `config plan`, `config apply`, and `audit
pull` invocation that reads live state, then supply the trusted target.

## Go API and module migration

Change the module dependency and imports to the v2 module path:

```go.mod
require github.com/orang-gaboets/octostate/v2 v2.0.0
```

Update imports to the v2 path, for example:

```go
import (
    "github.com/orang-gaboets/octostate/v2/pkg/gitops/apply"
    "github.com/orang-gaboets/octostate/v2/pkg/gitops/collector"
    "github.com/orang-gaboets/octostate/v2/pkg/gitops/plan"
)
```

The live GitOps entry points now require an independent expected-organization
argument:

```go
actual, err := collector.CollectOrganization(ctx, collectOptions, expectedOrg)
report, err := plan.Build(ctx, planOptions, expectedOrg)
check, err := apply.Check(ctx, applyOptions, expectedOrg)
result, err := apply.Execute(ctx, applyOptions, expectedOrg)
```

`CollectOrganizationForBootstrap`, `CollectOrganizationForSyncFromLive`, and
`CollectOrganizationForMaterialize` also require the expected organization.
There are no unbound variants of these live collection, planning, preflight, or
execution APIs. The expected login must come from trusted caller configuration
and match the organization in the desired configuration before GitHub services
are used.

`pkg/gitops/syncfromlive` functions transform an already collected state into
a local desired-state proposal and do not call GitHub. `pkg/gitops/diff.Build`
compares desired state with a stored snapshot. These data-only operations do
not perform live GitOps work. Lower-level `pkg/github` clients are available to
applications implementing their own GitHub behavior; callers using them do not
receive the target-binding guarantee provided by the GitOps entry points.

## Preserved behavior and boundaries

- Expected organization remains separate from desired state and is checked
  before authentication, live collection, preflight service access, or writes.
- Organization-local ownership validation remains in force for managed
  repositories, team memberships, and team repository permissions.
- Cross-organization repository templates remain supported as external
  references; the target binding does not make those repositories managed.
- The v2 module path is `github.com/orang-gaboets/octostate/v2`. Repository clone
  URLs and workflow source URLs continue to use the existing GitHub repository.

This release is the planned compatibility boundary for Issue #331. The change
does not require control-repository policy or workflow orchestration to move
into the Octostate engine.
