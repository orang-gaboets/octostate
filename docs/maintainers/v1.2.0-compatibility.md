# v1.2.0 Compatibility and Migration Notes

This document is the final compatibility list for the changes that shipped in
`v1.2.0`. It covers only concrete upgrade adaptations for existing
configuration, scripts, and machine consumers. Ordinary bug fixes and internal
implementation changes are intentionally excluded unless they require a user to
change released config or released integration behavior.

The qualifying v1.2.0 migration items are:

- repository topic-format rejection
- organization-local managed repository ownership
- duplicate invite identity rejection
- dependency-safe `config plan` repository ordering
- conditional `team members add` / `team members remove` stdout envelopes when #215 lands in `v1.2.0`
- `audit diff` team repository permission executability gating

The v1.2.0 audit also reviewed `#212` and `#235`. They are documented at the
end of this file as non-qualifying changes because they do not require a
released-config migration or a released-API/output adaptation.

## Repository Topic Validation

What changed:
v1.2.0 validates repository topics in `config/organization.yaml` before plan,
apply, proposal writes, and `sync-from-live --write`. Leading and trailing
whitespace is trimmed, then each topic must contain only lowercase ASCII
letters, digits, and hyphens. octostate no longer accepts uppercase, embedded
whitespace, slash, or underscore variants and silently carries them forward.

Why it matters:
An existing config that validated in `v1.1.1` can now fail immediately after an
upgrade.

Before (`v1.1.1` accepted this):

```yaml
organization: orang-gaboets
repositories:
  - name: octostate
    visibility: public
    topics: [Go]
```

After (`v1.2.0` requires valid topic content after trimming):

```yaml
organization: orang-gaboets
repositories:
  - name: octostate
    visibility: public
    topics: [go]
```

Remediation:
Lowercase every topic and remove embedded spaces, slashes, and underscores;
leading and trailing whitespace is trimmed automatically. Keep each topic within
GitHub's documented topic constraints before running `octostate config validate`.

Canonical docs:
[Config schema](../gitops/config-schema.md),
[Config commands](../cli/config.md)

## Organization-Local Managed Ownership

What changed:
Managed repository ownership is now organization-local. In desired state,
`repositories[].owner` and `teams[].repositories[].owner` must match the
top-level `organization` after trimming and case-folding. External
`template.owner` references remain valid because they are create-time inputs,
not managed ownership.

Why it matters:
Configs that previously declared cross-organization managed owners now fail
validation with `repository_owner_scope`.

Before (`v1.1.1` accepted explicit cross-org managed owners):

```yaml
organization: orang-gaboets
repositories:
  - owner: shared-platform
    name: octostate-template-consumer
    visibility: private
teams:
  - slug: platform
    name: Platform
    privacy: closed
    repositories:
      - owner: shared-platform
        name: octostate-template-consumer
        permission: push
```

After (`v1.2.0` keeps managed owners local, but external templates are still valid):

```yaml
organization: orang-gaboets
repositories:
  - name: octostate-template-consumer
    visibility: private
    template:
      owner: shared-platform
      name: repo-template
teams:
  - slug: platform
    name: Platform
    privacy: closed
    repositories:
      - name: octostate-template-consumer
        permission: push
```

Remediation:
If the managed target really belongs to the declared organization, remove the
redundant `owner` field or normalize it to the top-level `organization`. If it
truly belongs to another organization, move it out of this desired state.
Leave external `template.owner` values unchanged unless the template source
itself changed.

Canonical docs:
[Config schema](../gitops/config-schema.md),
[Primitive commands](../cli/primitives.md)

## Duplicate Invite Identity Rejection

What changed:
v1.2.0 rejects duplicate invite identities during validation. Comparison is
per identity kind after trimming: `username` vs `username`,
`email` vs `email`, and `user_id` vs `user_id`. Username and email matching are
case-insensitive within their own kind, but comparison does not cross identity
kinds.

Why it matters:
Configs that used duplicate pending invites as harmless duplicates now fail
validation.

Before (`v1.1.1` accepted both entries):

```yaml
organization: orang-gaboets
invites:
  - username: OctoCat
  - username: octocat
```

After (`v1.2.0` requires one entry per identity kind):

```yaml
organization: orang-gaboets
invites:
  - username: octocat
  - email: octocat@example.com
```

Remediation:
Deduplicate invites within each identity kind before upgrading. Keep only one
`username`, one `email`, or one `user_id` entry for the same trimmed
case-folded identity. If you intentionally need multiple invite forms for the
same person, use different identity kinds and keep each entry unique within its
own kind.

Canonical docs:
[Config schema](../gitops/config-schema.md),
[Config commands](../cli/config.md)

## Dependency-Safe `config plan` Ordering

What changed:
Repository actions in `config plan` now follow deterministic dependency-safe
ordering instead of a simpler operation-first ordering model. A required
template source create, or an update that enables `is_template: true`, is
emitted before dependent repository creates. Consumers should treat the emitted
repository action order as authoritative.

Why it matters:
Automation that re-sorts repository actions, or assumes all repository updates
precede all repository creates, can now break valid dependency ordering.

Before (fragile consumer post-processing):

```bash
octostate config plan --config-dir ./config --token "$GITHUB_TOKEN" \
  | jq '.executable_actions | sort_by(.resource_type, .operation, .resource_id)'
```

After (preserve the emitted order):

```bash
octostate config plan --config-dir ./config --token "$GITHUB_TOKEN" \
  | jq '.executable_actions'
```

Remediation:
Update any machine consumer of `config plan` or `config apply --dry-run` to
preserve repository action order exactly as emitted. Do not re-sort repository
actions by operation, and do not assume `update` always appears before
`create`.

Canonical docs:
[Config commands](../cli/config.md),
[GitOps overview](../gitops/overview.md),
[GitOps architecture](../gitops/architecture.md)

## `team members` Output Envelopes

What changed:
If #215 remains included in `v1.2.0`, live and dry-run `team members add` /
`team members remove` emit the standard `{status, message, data}` operation
envelope. A successful live `team members add` still includes the GitHub
membership response, but it now appears under `data.membership`.

Why it matters:
Scripts that parsed the old raw membership JSON or plain-text dry-run/remove
output must switch to the standard envelope.

Before (`v1.1.1` output shapes differed by path):

```json
{
  "State": "active",
  "Role": "member"
}
```

```text
Dry run: would remove user "alice" from team orang-gaboets/platform
```

After (`v1.2.0` uses one envelope shape):

```json
{
  "status": "success",
  "message": "Added user \"alice\" to team orang-gaboets/platform with role member",
  "data": {
    "organization": "orang-gaboets",
    "slug": "platform",
    "username": "alice",
    "role": "member",
    "membership": {
      "State": "active",
      "Role": "member"
    }
  }
}
```

```json
{
  "status": "dry-run",
  "message": "Dry run: would remove user \"alice\" from team orang-gaboets/platform",
  "data": {
    "organization": "orang-gaboets",
    "slug": "platform",
    "username": "alice"
  }
}
```

Remediation:
Update parsers to read `status`, `message`, and `data` first. For live
`team members add`, move any raw membership parsing to `data.membership`. For
dry-run and remove paths, stop expecting plain text on stdout.

Canonical docs:
[Primitive commands](../cli/primitives.md)

## `audit diff` Team Repository Permission Gating

What changed:
`audit diff` now gates team repository permission create/update actions on
repository availability in the stored snapshot or on a complete desired
template-backed create path. When the repository is unavailable, the action is
reported as non-executable with an availability diagnostic instead of appearing
executable by default.

Why it matters:
Offline drift consumers that treated every team repository permission
create/update as immediately executable must now honor the `executable` flag and
message for these actions too.

Before (older offline drift consumers could see the permission as executable):

```json
{
  "resource_type": "team_repo_permission",
  "operation": "update",
  "resource_id": "platform/orang-gaboets/octostate",
  "executable": true
}
```

After (`v1.2.0` reports missing repository availability explicitly):

```json
{
  "resource_type": "team_repo_permission",
  "operation": "update",
  "resource_id": "platform/orang-gaboets/octostate",
  "executable": false,
  "message": "team repository permission platform/orang-gaboets/octostate requires repository orang-gaboets/octostate to be available: repository orang-gaboets/octostate is absent from snapshot and desired state"
}
```

Remediation:
If you consume `audit diff` programmatically, treat `team_repo_permission`
actions the same way you already treat other gated actions: check
`executable`, surface `message`, and do not assume that every create/update is
ready to apply. If the repository should be available, refresh the snapshot
with `audit pull` or add the missing desired repository declaration first.

Canonical docs:
[Audit commands](../cli/audit.md),
[Config commands](../cli/config.md),
[GitOps architecture](../gitops/architecture.md)

## Audited Non-Qualifying Changes

The v1.2.0 audit also reviewed these landed changes and intentionally excluded
them from the migration list:

- `#212` aligns proposal-mode casing behavior and documents the existing role
  downgrade behavior for `team members add` when `--role` is omitted. This does
  not require a released-config migration and does not change the live/dry-run
  output contract that external consumers parse.
- `#235` normalizes programmatic desired state before reconciliation. It closes
  internal consistency gaps between programmatic callers and file-loaded config,
  but it does not require a new user config shape or a new machine-consumer
  adaptation for the released CLI surfaces.
