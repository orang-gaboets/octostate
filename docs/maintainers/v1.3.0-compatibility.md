# v1.3.0 Compatibility and Migration Notes

## Minimum Go Version

Starting with v1.3.0, the minimum Go version for source installation, embedding
in another Go program, and repository development is Go 1.26.11.
The module declares `go 1.26.11`, which also implies the `go1.26.11` toolchain.
The GO-2026-6859 `net/http` fix (an HTTP/1 server crash caused by a
`MaxBytesReader` header race) is included in Go 1.26.11 and Go 1.27.4, along
with the earlier GO-2026-6809 fix in `crypto/x509`. Use Go 1.26.11 or later in
the 1.26 series, or Go 1.27.4 or later; Go 1.27.0 through 1.27.3 meet the
module minimum but still contain the affected code. The `go` directive implies
the matching toolchain, so no explicit `toolchain` directive is needed.

Before upgrading from v1.2.0, update the Go installation used by developer
machines and CI to one of those fixed toolchains. Consumers embedding Octostate
must also allow their module's minimum Go version to rise to at least 1.26.11
when updating the dependency. Environments using `GOTOOLCHAIN=local` must
install a compatible toolchain explicitly; automatic toolchain switching is
disabled.

Users of prebuilt CLI archives do not need a Go installation. This toolchain
migration does not change Octostate's exported Go APIs, CLI flags, configuration
format, or command output.

## Reusable Configuration Review Workflow

The reusable configuration-review workflow now installs Go 1.26.11 and retains
`GOTOOLCHAIN=local`. Its workflow revision and the `octostate_version` input
are independent pins.

When selecting a v1.3.0 CLI commit or a commit requiring Go 1.26.11, also select
a trusted workflow revision containing this toolchain upgrade. An older
workflow revision that installs a toolchain below Go 1.26.11 cannot build that
CLI and fails during installation. The current workflow accepts only a reviewed,
full 40-character lowercase commit SHA for `octostate_version`; it rejects release
tags, branch names, abbreviated SHAs, and `latest`. Resolve a release tag to
its commit and review that commit before pinning it. Older workflow revisions
may retain the earlier tag-or-SHA input contract; caller behavior depends on
the pinned workflow commit.
